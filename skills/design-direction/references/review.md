# 设计复核与可选 Impeccable 集成

本文件改写并整合 Impeccable 的页面模式、设计评审与技术审计分离、局部修正和验收方法，来源见技能根目录 `NOTICE.md`。不是上游完整实现或兼容性承诺。

## 先判断，再看检测结果

先独立记录页面是否符合内容、任务、用户选择和整体阅读路线，再查看自动检测，减少被检测器的风格偏好牵引。单个助手也可以按此顺序执行，但不能称为独立双人评审。截图未打开、页面未访问、操作未执行的项目明确写未验证。

| 检查层 | 要回答什么 | 证据 |
| --- | --- | --- |
| 方向兑现 | 选中的结构和偏好是否落实？哪些发生了改变？ | 选择记录、整页及关键区域对比 |
| 整站设计 | 板块顺序、层级、导航、密度和阅读路线是否适合真实内容？ | 首页、关键内页、桌面和手机视图 |
| 使用质量 | 能否找到并完成核心任务？长标题、键盘和错误状态是否可用？ | 实际操作、浏览器检查、测量 |
| 模式线索 | 是否重复套用无意义的装饰或模板？ | 下面的问题表与可选检测结果 |

## 去 AI 味问题表

信号只触发判断，不构成自动删除指令。颜色、字体或组件的出现不能证明作品由 AI 生成。

| 信号 | 判断与改法 | 合理保留的情况 |
| --- | --- | --- |
| 巨大首屏、数字、三张卖点卡、评价、CTA 固定排列 | 每区是否有真实内容和任务；用文章索引、项目列表等适配内容 | 真实转化路径确实需要这些板块 |
| 所有信息同权重、卡片套卡片 | 看能否用分组、留白、列表/表格减少层级；必要信息不能一起删掉 | 需要独立比较的对象或有意义的嵌套关系 |
| 紫色光晕、奶油色衬线、粗边硬阴影等流行组合 | 检查是不是仅替换皮肤，结构仍与内容无关 | 明确的品牌或用户选择，并且层级和可用性成立 |
| 标签、序号、巨大图标、边缘色条泛滥 | 是否表达状态、顺序、定位或识别；没有信息就减少 | 分类标签、步骤编号、状态指示确有用途 |
| 标题过大、灰字过淡、留白过量 | 用真实中文长标题和手机宽度测试字号、行长、对比度和密度 | 展示型页面有意使用大字，且没有挤走关键操作 |
| 每块相同的入场动效、内容默认隐藏 | 保证内容可达、减少等待、处理减少动态效果和脚本失败 | 动效表达关系、反馈或作品本身且不阻挡使用 |
| 空泛标题、虚构数字、重复说明 | 换成真实项目材料、明确动作和恢复路径 | 演示数据明确标注，未冒充事实 |
| 首屏好看，内页和交互残缺 | 优先完成导航、内容页和核心操作，再做装饰 | 仅当交付范围确实只有静态概念稿，明确标记 |

## 记录与修正

通常只报告最重要的 3–5 项；按阻断任务、明显使用困难、结构/一致性、局部打磨排序。每项写：位置、证据、影响、具体修正、如何回测。把主观偏好分歧与实测缺陷分开。不输出假精确的“AI 味分数”或未经测量的性能/可访问性结论。

按以下顺序改：核心任务与真实内容 → 板块和导航 → 排版与密度 → 颜色/组件一致性 → 装饰与动态效果。保留范围外内容和既有品牌，不把局部 polish 偷换成重设计。

修正后复查相同视图和操作。截图需加载完成、位置正确、文字可读；整页缩略图不能代替关键区域检查。截图失败先重新获取证据，不把黑屏当成页面缺失。无效/过期证据不支撑验收。没有新问题或变更就不重复检测；达到验收条件就停止，仍有问题则列出未解决项。

## 何时借助 Impeccable

若用户项目已经安装 Impeccable，按任务读取它的对应技能，不复制整套工具链：

| 需求 | 可选上游能力 |
| --- | --- |
| 确定页面任务与范围 | `shape` / `init`，复用已有简报，避免重复询问 |
| 判断设计是否贴合内容 | `critique` |
| 结构、字体、颜色失衡 | `layout` / `typeset` / `colorize` |
| 太平淡或太吵 | `bolder` / `quieter`，保持既定身份 |
| 内容和流程冗余 | `distill` / `clarify` / `onboard` |
| 手机、长文本、失败状态 | `adapt` / `harden` |
| 技术质量与最终打磨 | `audit` / `optimize` / `polish` |
| 同一局部比较不同做法 | `generate` / `live`，仅在本地开发项目使用 |
| 保存已实现的设计系统 | `document` / `extract` |

没有安装时照常执行本技能，不要求安装才能继续。本技能不自动安装、不配置 hooks、不启动远程方向目录，也不把上游命令名伪装成自己的已实现能力。

### 检测器适配约定

已经有可用的 `impeccable` 命令时，在目标项目目录运行，例如：

```sh
impeccable detect --json src/
impeccable detect --json http://localhost:5173
```

这是独立 CLI；`shape`、`critique` 等是助手内技能动作，不能假设 `impeccable critique` 是同样可运行的 CLI 子命令。安装方式以当前上游文档为准。

- 源码扫描与渲染页扫描覆盖不同。只扫源码不能声称移动端、手势、实际对比度已通过。
- 已有 hook 提供的最新同范围结果可以复用，不重复跑一遍只为凑流程。
- 退出码 `0` 表示该范围没有报告项；`2` 表示有报告项；`1` 表示扫描目标出错。不能把退出码 2 当作引擎故障，也不能把失败时的空 JSON 当作通过。
- 保留规则 ID、文件/元素位置和证据。重复报告先归并再判断，不用原始数量冒充严重程度。
- 用户明确保留的视觉选择记录理由，只对对应规则和范围作例外；不要为了“清零”全局关闭检测。
- `--no-config` 在本次研究版本中也会禁用 inline ignores。测试例外时不能用它，原始扫描结果与按项目例外过滤的结果必须区分。
- 规则通过只代表检测范围内未发现问题；仍需对照设计简报和核心任务验收。

适配依据：上游提交 `4f956490f0056ae1ff5ea80372cf56e83c001d3c`，npm shim 4.8.0 / engine 0.1.18。真实命令行为测试见项目 `research/impeccable.md`。未完成上游全链路、hooks 或 live 模式安装验收。
