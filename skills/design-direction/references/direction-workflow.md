# 从看参考到选定设计方向

## 1. 确定设计承载什么

优先读取现有需求和代码。信息不足时，用一句话询问用途、主要内容和访客最重要的操作；不要要求用户先选字体、色值或设计流派。

内容要有量级：5 个项目还是 50 个，3 篇文章还是 200 篇，有无真实照片和封面，标题是否以中文为主。资产不足时，指出某方向需要补哪些素材，不用虚构客户、评价、销量或数据填补。

区分新建、整站重设计、已有系统内的新页面、局部修改。后两种继承已确认的视觉语言。用户说“你决定”时，明确合理假设后推进；正在等待用户选择时，沉默不能视为选中。

## 2. 形成少量、可比较的方案

先按页面任务、内容量、资源和可访问性筛选真实参考，再寻找结构差异。通常展示 2–3 个可行方案，数量不足就说明原因，不能用不合适案例凑数。

每个方案用相同格式、相近展示面积说明：

- **日常名称和组织方式**：例如“侧栏定位，右侧连续阅读”，避免只写“高级极简”。
- **真实来源与证据**：原站、具体页面、查看日期、桌面/移动端/内页覆盖；展示可用的整页证据，不只截大标题。
- **内容路线**：第一眼看到什么，下方板块顺序，如何进入内页、返回和继续探索。
- **迁移示意**：把用户自己的内容放入文字线框或结构草图，明确标为提案。没有截图就提供原站链接并说明视觉待验证。
- **适配与代价**：适合什么内容量，需要哪些照片、插画或开发投入；移动端如何变化；已知风险。
- **保留与避开**：借鉴哪条组织原则，原站哪些部分不适合照搬。

至少在信息布局、密度、导航或板块节奏上形成实质差别；仅换颜色不算不同方向。不同方案使用同一份用户内容，避免素材精美程度替代结构比较。推荐理由应可复述，不能靠“最有高级感”。

不强制抽签、不预设固定风格套餐。用户要熟悉的布局可以照常使用。允许鲜明色彩、强动效和实验布局，前提是符合用途且有可用退路。

## 3. 让用户表达具体偏好

用普通话询问“哪个最接近？可以喜欢 A 的布局、B 的颜色，也可以都不要”。可反馈布局、信息密度、字体气质、颜色、图像、动效，不要求一次全部回答。

对“都不喜欢”，先用一轮问题定位偏差：太空、太挤、像海报、导航难找、太冷、动效太多，或内容根本不合适。排除已经否定的方案，改变搜索方向。不要换名字后再次给同一类布局。连续两轮仍不贴合时，缩小到一个板块/阅读路线比较，不无限展示新链接。

混合参考时选一个主结构，说明其它参考改变的局部及冲突。不能把三个网站各截一块就声称系统协调。

## 4. 留下可追踪的选择记录

在项目已有设计简报中记录，或新建 `DESIGN-BRIEF.md`。按项目规模精简，但关键约定不能遗漏：

```markdown
# 设计简报
状态：提案 / 用户已选择 / 用户授权助手决定
目标页面与模式：逐页记录 read / operate / persuade / experience
访客、核心任务、内容量及现有素材：
约束与不可改动项：

## 选择记录
用户原话：仅记录实际收到的反馈
主结构：参考 ID、URL、具体借鉴点和证据范围
辅助参考：借鉴颜色/排版等哪一部分，如何与主结构统一
拒绝项：参考 ID 或具体特征，拒绝理由
助手推断：与用户已确认选择分开

## 页面结构
导航与页面关系：
首页：每个板块的内容、作用、顺序和入口
关键内页：阅读/操作路线、返回与继续探索
移动端：重排、收起、保留、图片裁切、可用操作

## 视觉与交互约定
字体角色及中文覆盖、颜色角色、内容宽度、间距节奏：
图像来源及未具备的素材：
交互、焦点、加载/空/错误状态、减少动态效果：
一个值得记住的细节及其作用（有必要才设）：

## 验收映射
偏好/任务 | 具体实现位置 | 如何核查 | 结果或未验证项
```

没有真正用户选择就不能写“已确认”。不把一次任务的偏好升级成永久偏好。后续用户修正优先，留下变更原因即可，不重做整轮访谈。

## 5. 交给实现与复核

默认用代码和线框落实布局。用户需要视觉探索且工具支持时，可提供明确标记的概念图；图像不能替代内页设计或实际交互。沿用已选方向，避免实现时又退回大字首屏和等大卡片。

实现后逐条核对选择记录：A 的连续阅读结构是否仍在，B 的颜色如何分配到角色，用户否定的海报式首屏是否又出现。将具体遗漏交给 `review.md` 的修正流程。
